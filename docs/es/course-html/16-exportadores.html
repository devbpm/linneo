Capítulo 16 Exportar a PostgreSQL, OpenAPI y ODCS

Duración estimada:
75 minutos
Parte V:
Integración y práctica

La clasificación es más útil cuando llega a las herramientas que rodean al código: la base de datos que guarda los valores, la descripción de la API que los publica y el contrato de datos que leen otros equipos. Este capítulo presenta los tres exportadores de Linneo, que escriben el texto que espera cada una de esas herramientas, y enseña a integrarlos sin perder el control de lo que se publica.

Objetivos de aprendizaje

Al terminar este capítulo serás capaz de:

  • generar con PostgresAnonymizer las reglas de enmascaramiento de PostgreSQL Anonymizer que siguen una política de divulgación;
  • declarar funciones y valores de sustitución para tus columnas, incluidas las columnas NOT NULL, y prever qué regla recibe una columna que guarda varios campos;
  • añadir a la descripción OpenAPI de una API la extensión x-linneo de cada propiedad con OpenApiExtension;
  • escribir con OdcsSchema la sección schema de un contrato de datos del Open Data Contract Standard a partir de un inventario de datos;
  • alimentar los tres exportadores desde el código o desde un inventario guardado;
  • explicar qué hace cada exportador y qué queda en manos de la aplicación.

Antes de empezar

Este capítulo usa la política de divulgación del capítulo 7 (DisclosurePolicy y sus tratamientos CLEAR, MASK y OMIT) y el inventario de datos del capítulo 8. Los ejemplos usan el modelo de la universidad y la taxonomía estándar; las salidas son las reales de ese modelo.

Tres exportadores, un mismo principio

Los catálogos de datos del capítulo 17 publican la taxonomía. Los exportadores de este capítulo publican la clasificación de los campos de un modelo en las herramientas que acompañan al código.

Tabla 16.1. Los tres exportadores
ClasePaqueteEscribe
PostgresAnonymizerio.github.devbpm.linneo.export.postgresql Las sentencias SECURITY LABEL de PostgreSQL Anonymizer que enmascaran u omiten cada columna según una política.
OpenApiExtensionio.github.devbpm.linneo.export.openapi La extensión x-linneo de cada propiedad de la descripción de una API, como mapas o como JSON.
OdcsSchemaio.github.devbpm.linneo.export.odcs La sección schema de un contrato de datos ODCS v3, a partir de un inventario, como JSON.

Los tres comparten cinco características:

  1. Escriben texto y nada más. Ninguno se conecta a una base de datos, lee o escribe la descripción de la API, edita un contrato ni hace llamadas de red. La aplicación decide a qué columna, propiedad o contrato pertenece cada campo y aplica el resultado.
  2. La protección sale de la clasificación, nunca de los valores: un campo se describe por su categoría, sus niveles efectivos y su marca de secreto.
  3. Dos entradas. Una ClassClassification o una FieldClassification describe lo que declara el código ahora. Un InventoryField resuelto con una Taxonomy describe lo que una aplicación guardó, de modo que el mismo exportador funciona en un back office sin las clases del modelo. PostgresAnonymizer y OpenApiExtension aceptan ambas; OdcsSchema lee el inventario.
  4. Una clase con errores se rechaza. Cuando un exportador recibe una ClassClassification con errores, lanza IllegalArgumentException, porque un campo con un error no tiene clasificación y quedaría sin protección.
  5. Los campos exentos no contienen datos. PostgresAnonymizer les da una etiqueta sin regla, OpenApiExtension no les da extensión y OdcsSchema los deja fuera.

PostgreSQL Anonymizer: PostgresAnonymizer

Para qué sirve

Los entornos de pruebas suelen trabajar con copias de los datos de producción. PostgreSQL Anonymizer es una extensión de PostgreSQL que enmascara columnas en vistas enmascaradas y en volcados anonimizados a partir de etiquetas de seguridad: una sentencia SECURITY LABEL FOR anon ON COLUMN ... por columna dice cómo se enmascara. Escribir esas sentencias a mano repite la clasificación en otro sitio, con el riesgo de que se desvíen. PostgresAnonymizer las genera a partir de la clasificación y de una DisclosurePolicy.

De un tratamiento a una regla

La política decide el tratamiento de cada campo, y el anonimizador lo convierte en una regla:

Tabla 16.2. La regla de cada tratamiento
TratamientoRegla
OMITMASKED WITH VALUE NULL, o el valor declarado para la categoría con withValue.
MASKMASKED WITH FUNCTION ... si Linneo conoce una función para la categoría o un ancestro; si no, lo mismo que OMIT.
CLEARNinguna: la sentencia es ... IS NULL;, que elimina cualquier regla de la columna.

Un campo enmascarado se sustituye por un valor falso del mismo tipo cuando Linneo conoce una función para él. Si no la conoce, lo omite: Linneo no sabe el tipo de la columna, y omitir el valor es la opción más estricta. Las funciones que conoce son las funciones dummy_* que recomienda la versión 2 de PostgreSQL Anonymizer; las devuelve masks():

Tabla 16.3. Funciones de enmascaramiento incluidas
CategoríaFunción
user.account.usernameanon.dummy_username()
user.contact.address.cityanon.dummy_city_name()
user.contact.address.countryanon.dummy_country_name()
user.contact.address.postal_codeanon.dummy_post_code()
user.contact.address.stateanon.dummy_state_name()
user.contact.address.streetanon.dummy_street_name()
user.contact.emailanon.dummy_safe_email()
user.contact.phone_numberanon.dummy_phone_number()
user.device.ip_addressanon.dummy_ip()

user.name.firstanon.dummy_first_name()
user.name.lastanon.dummy_last_name()

Una función se busca por la clave de la categoría y, si no hay, por la de su madre, y así hacia arriba en el árbol. Lo mismo vale para los valores de sustitución.

La API

Tabla 16.4. Miembros de PostgresAnonymizer
MiembroDescripción

withMask y withValue no modifican el anonimizador: devuelven uno nuevo. Las instancias son inmutables y seguras entre hilos.

Un ejemplo con Student

La aplicación decide la columna de cada campo. En la universidad, las columnas usan nombres en minúsculas separados por guiones bajos (first_name para firstName), así que una función pequeña traduce la ruta:

SECURITY LABEL FOR anon ON COLUMN "students"."created_at" IS NULL;
SECURITY LABEL FOR anon ON COLUMN "students"."updated_at" IS NULL;
SECURITY LABEL FOR anon ON COLUMN "students"."version" IS NULL;
SECURITY LABEL FOR anon ON COLUMN "students"."created_by" IS 'MASKED WITH FUNCTION anon.dummy_username()';
SECURITY LABEL FOR anon ON COLUMN "students"."id" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."national_id" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."first_name" IS 'MASKED WITH FUNCTION anon.dummy_first_name()';
SECURITY LABEL FOR anon ON COLUMN "students"."last_name" IS 'MASKED WITH FUNCTION anon.dummy_last_name()';
SECURITY LABEL FOR anon ON COLUMN "students"."email" IS 'MASKED WITH FUNCTION anon.dummy_safe_email()';
SECURITY LABEL FOR anon ON COLUMN "students"."date_of_birth" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."disability_degree" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."analytics_id" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."academic_status" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "students"."counselling_notes" IS 'MASKED WITH VALUE NULL';

Cómo leer la salida:

  • Una sentencia por columna. Cada columna recibe exactamente una sentencia, también las de los campos que se muestran tal cual.
  • Primero las eliminaciones. Las sentencias IS NULL, que quitan una regla, van antes que las de enmascaramiento, cada grupo en el orden del primer campo de su columna. Por eso created_by, que la política enmascara, aparece después de version.
  • Funciones conocidas. Nombre, apellido, correo y usuario reciben un valor falso de su tipo.
  • Omisión cuando no hay función. national_id o academic_status se enmascaran según la política, pero Linneo no conoce una función para su categoría y los deja en NULL. disability_degree es NULL porque la política lo omite.

Ejecutar de nuevo las sentencias tras un cambio de la clasificación o de la política pone todas las columnas al día: IS NULL elimina las reglas que ya no corresponden.

Funciones y valores propios

withMask declara una función para una categoría y las que cuelgan de ella, salvo que una clave más específica tenga la suya. withValue declara el valor que sustituye a NULL en los valores omitidos. Este segundo método es imprescindible en las columnas NOT NULL, como el hash de contraseña de Staff, que rechazarían NULL. El valor debe ser una constante que no diga nada del original.

Un extracto de la salida, sin las cuatro primeras sentencias, que son como las de students:

SECURITY LABEL FOR anon ON COLUMN "staff"."id" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "staff"."full_name" IS 'MASKED WITH FUNCTION anon.dummy_name()';
SECURITY LABEL FOR anon ON COLUMN "staff"."work_email" IS 'MASKED WITH FUNCTION anon.dummy_safe_email()';
SECURITY LABEL FOR anon ON COLUMN "staff"."job_title" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "staff"."department" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "staff"."social_security_number" IS 'MASKED WITH FUNCTION anon.partial(social_security_number, 2, ''********'', 2)';
SECURITY LABEL FOR anon ON COLUMN "staff"."iban" IS 'MASKED WITH FUNCTION anon.partial(iban, 4, ''******'', 2)';
SECURITY LABEL FOR anon ON COLUMN "staff"."sex_offence_certificate_clear" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "staff"."password_hash" IS 'MASKED WITH VALUE ''*''';

La función declarada para user.government_id sirve a user.government_id.social_security_number. Las comillas simples de las reglas se duplican dentro de la etiqueta. staffRules.rule(...) devuelve el texto de la regla sin la sentencia: para passwordHash, MASKED WITH VALUE '*'; para version, null.

Atención

Una función declarada para una categoría llega a todas sus descendientes. Con withMask(USER_EDUCATION, "anon.random_int_between(0, 10)"), la columna grades.course_code (user.education.course_history), que guarda un texto, también recibe un entero aleatorio. Declara la función en la clave más específica que la necesite: con withMask(USER_EDUCATION_GRADE, ...), course_code queda en MASKED WITH VALUE NULL y solo mark recibe la función.

Columnas compartidas

Varios campos pueden guardarse en una sola columna, por ejemplo un compuesto guardado como JSON. La función columns devuelve entonces la misma columna para todos ellos, y la columna recibe una sentencia: MASKED WITH VALUE NULL salvo que todos los campos se muestren tal cual, aunque cada uno tenga su propia función. Un valor falso del tipo de un campo no sirve en una columna que contiene varios.

SECURITY LABEL FOR anon ON COLUMN "scholarship_applications"."id" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "scholarship_applications"."home" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "scholarship_applications"."previous" IS 'MASKED WITH VALUE NULL';
SECURITY LABEL FOR anon ON COLUMN "scholarship_applications"."billing" IS 'MASKED WITH VALUE NULL';

home.street, home.city y home.postalCode tienen cada uno una función dummy_*, pero comparten la columna home, que recibe NULL. Al revés, si todos los campos de una columna se muestran tal cual, como los de configuración de MenuGroup guardados en una columna settings, la columna recibe IS NULL. Una función columns que devuelve null deja el campo sin sentencia, para los campos que no tienen columna propia.

Nombres de columna

Una columna se escribe tabla.columna o esquema.tabla.columna, y cada parte es un identificador simple o uno entre comillas dobles. Las sentencias escriben siempre las partes entre comillas, y pasan a minúsculas una parte sin comillas, como hace PostgreSQL al leerla. Así funcionan las palabras reservadas, y la sentencia nombra la misma columna que la base de datos:

Tabla 16.5. Cómo se escribe una columna
Columna recibidaEn la sentencia
Students.Email"students"."email"
"Students"."e-mail""Students"."e-mail"
auth.user.email"auth"."user"."email"
emailIllegalArgumentException: falta la tabla.
students.email; DROP TABLE studentsIllegalArgumentException: no es un identificador cualificado.

El mensaje de los dos últimos casos es Not a qualified column name (table.column): .... Esta comprobación impide que una sentencia lleve otra cosa que la etiqueta. Una parte de más de 63 bytes en UTF-8 también se rechaza: PostgreSQL conserva solo los 63 primeros bytes de un nombre, así que dos nombres largos podrían ser la misma columna.

La etiqueta es una constante de cadena que se lee igual sea cual sea standard_conforming_strings: una regla con una barra invertida se escribe como cadena de escape (E'...') con la barra duplicada.

Si dos grafías distintas nombran la misma columna, por ejemplo public.students.email y students.email, Linneo no puede saberlo y escribe dos sentencias. Como las eliminaciones van primero, la regla de enmascaramiento es la que queda.

Desde un inventario guardado

labels(inventory, object, taxonomy, columns) escribe las mismas sentencias a partir de un inventario, sin las clases del modelo. El conjunto de sentencias es el mismo que el de la clasificación; el orden dentro de cada grupo sigue el del inventario, que va por ruta. tables es el mapa de clases a tablas del capítulo 8:

DataInventory inventory = classifier.inventory(List.of(Student.class, Staff.class), tables::get);
List<String> statements = PostgresAnonymizer.of(DisclosurePolicy.forLogs())
        .labels(inventory, "students", taxonomy, path -> column("students", path));

Un objeto que no está en el inventario lanza IllegalArgumentException con el mensaje The inventory has no object 'teachers': una clave mal escrita no puede producir en silencio una lista vacía de sentencias.

Integrarlo

  1. Elige la política del canal. Para una copia de pruebas, forLogs() es un buen punto de partida; si el equipo de pruebas necesita más datos en claro, construye otra con DisclosurePolicy.builder().
  2. Declara con withMask las funciones de las columnas que Linneo no conoce y con withValue los valores de las columnas NOT NULL.
  3. Genera las sentencias de todas las tablas, desde las clases o desde el inventario guardado.
  4. Ejecuta las sentencias con la herramienta de base de datos de la aplicación, en el script que prepara la copia de pruebas, cada vez que cambie la clasificación o la política.

Protección de datos

Las sentencias aplican la política a una copia, pero no la convierten en anónima por sí mismas: lo que se deja en claro sigue ahí, y una combinación de columnas en claro puede identificar a una persona. Linneo hace explícita la decisión columna a columna y la mantiene al día con el código; valorar si el resultado es suficiente para el uso previsto corresponde a los responsables del tratamiento y al delegado de protección de datos.

Límites

  • No conoce los tipos de las columnas: sin una función declarada, un valor enmascarado se omite.
  • No sabe en qué columna está cada campo: lo dice la función columns de la aplicación.
  • No ejecuta nada ni comprueba que la extensión esté instalada: escribe sentencias.
  • Solo conoce las funciones de la Tabla 16.3; las demás las declaras tú.

La extensión OpenAPI: OpenApiExtension

Para qué sirve

Los datos que devuelve una API son datos que salen del sistema. Una descripción OpenAPI dice el tipo de cada propiedad, pero no qué datos personales lleva ni cuánta protección necesita. OpenApiExtension añade esa información como una extensión de la especificación, con el nombre de la constante OpenApiExtension.NAME, "x-linneo". Quien consulte la descripción, una persona o una herramienta, sabe así qué propiedades contienen datos personales.

Los objetos de transferencia de la API se clasifican como cualquier clase, normalmente con @DerivedFrom, de modo que una vista de una entidad toma la clasificación de los campos que copia.

La extensión

El valor de la extensión es un objeto con estos miembros, en este orden:

Tabla 16.6. Miembros de la extensión x-linneo
MiembroPresenteValor
categorysiempreLa clave de la categoría.
personalsiempretrue si el campo contiene datos personales.
naturesolo en datos personalesORDINARY, SPECIAL_CATEGORY o CRIMINAL_OFFENCE.
confidentiality, integritysiempreLos niveles efectivos del campo.
identifiabilitysolo en datos personalesIDENTIFIED o PSEUDONYMIZED.
secretsiempretrue si el campo contiene un secreto.

Los valores son cadenas y booleanos, que cualquier biblioteca de OpenAPI puede añadir a una propiedad. La extensión también es válida en un JSON Schema, que ignora las palabras clave desconocidas.

La API

La clase no tiene constructor público ni estado: todos sus métodos son estáticos.

of(FieldClassification field)
La extensión de una propiedad, como un mapa inmutable en orden estable.
of(InventoryField field, Taxonomy taxonomy)
La extensión de un campo guardado; un mapa vacío para un campo exento. TaxonomyException si la taxonomía no contiene la clave.
of(ClassClassification classification)
Las extensiones de todos los campos clasificados de una clase, por ruta y en el orden de los campos; los exentos no tienen. IllegalArgumentException si la clase tiene errores.
toJson(ClassClassification classification)
Lo mismo como un objeto JSON, para herramientas que no están escritas en Java.

Un ejemplo con una vista de estudiante

La API de secretaría devuelve una vista reducida del estudiante. Sus campos derivan de Student, y uno de ellos, examAdaptation, indica si el estudiante tiene adaptación de exámenes, un valor calculado a partir del grado de discapacidad:

import io.github.devbpm.linneo.export.openapi.OpenApiExtension;

ClassClassification view = classifier.classify(StudentView.class);
Map<String, Map<String, Object>> extensions = OpenApiExtension.of(view);
extensions.forEach((path, extension) -> System.out.println(path + " " + extension));

id {category=user.unique_id, personal=true, nature=ORDINARY, confidentiality=LOW, integrity=MEDIUM, identifiability=IDENTIFIED, secret=false}
firstName {category=user.name.first, personal=true, nature=ORDINARY, confidentiality=LOW, integrity=MEDIUM, identifiability=IDENTIFIED, secret=false}
email {category=user.contact.email, personal=true, nature=ORDINARY, confidentiality=LOW, integrity=MEDIUM, identifiability=IDENTIFIED, secret=false}
academicStatus {category=user.education.status, personal=true, nature=ORDINARY, confidentiality=MEDIUM, integrity=HIGH, identifiability=IDENTIFIED, secret=false}
examAdaptation {category=user.health_and_medical.disability, personal=true, nature=SPECIAL_CATEGORY, confidentiality=HIGH, integrity=HIGH, identifiability=IDENTIFIED, secret=false}
page {category=system.operations, personal=false, confidentiality=LOW, integrity=LOW, secret=false}

Tres observaciones:

  • examAdaptation es un booleano, pero hereda la categoría especial de su fuente. La descripción de la API lo dice, y quien la lea sabrá que esa respuesta revela datos de salud.
  • page no es personal, así que su extensión no tiene nature ni identifiability.
  • links, exento, no tiene extensión.

OpenApiExtension.toJson(view) da lo mismo como JSON, en una sola línea. Un extracto:

{"id":{"category":"user.unique_id","personal":true,"nature":"ORDINARY","confidentiality":"LOW","integrity":"MEDIUM","identifiability":"IDENTIFIED","secret":false},"firstName":{...}}

En el extracto, {...} sustituye al resto del objeto, que sigue el mismo patrón para cada campo.

Integrarlo

Linneo no lee ni escribe la descripción de la API. La aplicación asigna cada ruta de campo a su propiedad, que puede tener otro nombre o estar anidada, y añade la extensión con la biblioteca que ya usa. Con springdoc, un OpenApiCustomizer recorre las propiedades del esquema:

springdoc y swagger-core son dependencias de la aplicación, no de Linneo, que no tiene ninguna. Una herramienta que no está escrita en Java toma el JSON de toJson, escrito durante la compilación donde pueda leerlo. Un back office que guarda un inventario usa of(InventoryField, Taxonomy), que da la misma extensión que la clasificación del campo.

Límites

  • Describe, no protege: la extensión informa, pero no impide que la API devuelva un dato.
  • No sabe qué propiedad corresponde a cada campo: una propiedad renombrada o anidada la asigna la aplicación.
  • Un compuesto aparece con rutas campo.parte, que la aplicación debe llevar a sus propiedades anidadas.

El contrato de datos: OdcsSchema

Para qué sirve

Un contrato de datos es el acuerdo entre quien produce un conjunto de datos y quien lo consume: qué objetos y propiedades contiene, quién es responsable y cómo debe tratarse. El Open Data Contract Standard (ODCS) es un formato abierto para escribirlo. OdcsSchema escribe la sección schema de un contrato ODCS v3 a partir de un inventario de datos: un objeto de esquema por cada objeto del inventario y una propiedad por cada campo clasificado. Así el contrato dice qué contiene cada propiedad y cómo debe protegerse.

Qué dice una propiedad

Cada propiedad lleva cuatro miembros:

name
La ruta del campo (home.street en una parte de un compuesto).
classification
Una etiqueta de la escala habitual de cuatro niveles, según la confidencialidad (Tabla 16.7).
tags
La clave de la categoría y, cuando corresponde, personal-data, special-category, criminal-offence-data y secret.
customProperties
linneo.category, linneo.confidentiality, linneo.integrity y, solo en datos personales, linneo.identifiability, cada una como {"property": ..., "value": ...}.
Tabla 16.7. La etiqueta classification
Confidencialidadclassification
PUBLICpublic
LOWinternal
MEDIUMconfidential
HIGHrestricted
cualquiera, con un secretorestricted

Los niveles son los efectivos: los de la categoría, con la elevación que declare el campo. El método estático OdcsSchema.classification(Protection) da la etiqueta de cualquier protección.

La API

static OdcsSchema of(Taxonomy taxonomy)
El escritor para una taxonomía, que resuelve las claves que guarda el inventario.
String schemaJson(DataInventory inventory)
La sección schema: una lista JSON con un objeto de esquema por objeto del inventario, en su orden.
String objectJson(DataInventory inventory, String object)
El objeto de esquema de un objeto, con name, logicalType (object) y properties.
String propertyJson(InventoryField field)
La propiedad de un campo clasificado.

Las instancias son inmutables y seguras entre hilos.

  "logicalType": "object",
  "properties": [
    {
      "name": "averageMark",
      "classification": "confidential",

Objetos desconocidos, campos exentos y claves que faltan

OdcsSchema sigue el mismo criterio de fallo seguro que el resto de Linneo: lo que no puede describir con certeza lo rechaza en lugar de omitirlo en silencio.

  • Un objeto desconocido. objectJson(inventory, "teachers") lanza IllegalArgumentException con el mensaje The inventory has no object 'teachers', en lugar de devolver un objeto de esquema vacío.
  • Un campo exento. schemaJson y objectJson lo dejan fuera, porque no contiene datos. Pedir su propiedad con propertyJson lanza IllegalArgumentException; para documents.fileStore, el mensaje es documents.fileStore exempt: cliente del almacén de archivos, se abre bajo demanda is exempted and holds no data.
  • Una clave que la taxonomía no contiene. Un inventario guardado con user.contact.fax, resuelto con la taxonomía estándar, lanza TaxonomyException con el mensaje Unknown data category 'user.contact.fax'. Antes de publicar, resuelve las claves obsoletas o eliminadas como explica el capítulo 8.

Integrarlo

El resultado es JSON, que también es YAML válido. Incorpóralo al contrato bajo la clave schema:, o escríbelo en un fichero que incorpore la compilación del contrato. Linneo no conoce los servidores, los tipos de las propiedades ni los responsables del contrato: esa parte la mantiene el equipo que publica los datos. Como el esquema sale del inventario, sigue a la clasificación: regenéralo cuando InventoryDiff informe cambios, y la revisión del contrato mostrará el cambio de una clasificación como un cambio del contrato.

Límites

  • Solo escribe la sección schema, y en ella solo la clasificación de cada propiedad.
  • Los nombres de las propiedades son las rutas de los campos; si el contrato usa otros, la aplicación los asigna.
  • Lee un inventario, no clases: construye el inventario con Classifier.inventory o léelo de la copia guardada.

Errores frecuentes

Esperar que Linneo ejecute las sentencias o actualice la descripción de la API.
Los exportadores escriben texto. La aplicación ejecuta las sentencias, añade las extensiones y publica el contrato.
Declarar una función de enmascaramiento en una categoría demasiado general.
Llega a todas las descendientes, aunque guarden otro tipo de valor. Decláralas en la clave más específica.
Olvidar withValue en una columna NOT NULL.
El valor omitido es NULL y la columna lo rechaza. Declara una constante que no diga nada del original, como '*'.
Pasar a labels una función de columnas que construye el SQL a mano.
columns devuelve nombres, no sentencias. Un nombre que no sea un identificador cualificado se rechaza.
Construir una columna compartida y esperar una función dummy_*.
Una columna con varios campos recibe NULL salvo que todos se muestren tal cual.
Publicar el esquema ODCS de un inventario con claves que la taxonomía ya no tiene.
OdcsSchema lanza TaxonomyException. Concilia el inventario antes de publicar.
Tratar la extensión x-linneo como un control de acceso.
Describe la protección que necesita una propiedad, pero no impide que la API la devuelva.

Resumen

  • Los tres exportadores escriben texto a partir de la clasificación o de un inventario guardado, y no se conectan a nada.
  • PostgresAnonymizer convierte una DisclosurePolicy en sentencias SECURITY LABEL de PostgreSQL Anonymizer: una por columna, primero las que eliminan reglas y después las que enmascaran.
  • OMIT da MASKED WITH VALUE NULL o el valor declarado con withValue; MASK, una función conocida o declarada con withMask, y si no la hay, lo mismo que OMIT; CLEAR, IS NULL.
  • Una columna compartida es NULL salvo que todos sus campos sean CLEAR. Los identificadores se escriben entre comillas, en minúsculas si venían sin comillas, y con un máximo de 63 bytes.
  • OpenApiExtension da la extensión x-linneo de cada propiedad, con la categoría, la naturaleza, los niveles, la identificabilidad y el secreto.
  • OdcsSchema escribe la sección schema de un contrato ODCS v3 desde un inventario, con classification, tags y customProperties, y rechaza objetos desconocidos.

Ejercicios

  1. Una función demasiado general. Con la política para logs, ¿qué regla recibe Enrollment.tuitionFee? Si declaras withMask(USER_FINANCIAL, "anon.random_int_between(100, 3000)") para enmascarar el importe, ¿qué otra columna de enrollments recibe esa función y por qué es un problema?

    Solución del ejercicio 1

    Sin declarar nada, MASKED WITH VALUE NULL: la política enmascara el importe, pero Linneo no conoce una función para user.financial.fee. Con la función declarada en user.financial, también la recibe scholarship_type (user.financial.scholarship):

    SECURITY LABEL FOR anon ON COLUMN "enrollments"."tuition_fee" IS 'MASKED WITH FUNCTION anon.random_int_between(100, 3000)';
SECURITY LABEL FOR anon ON COLUMN "enrollments"."scholarship_type" IS 'MASKED WITH FUNCTION anon.random_int_between(100, 3000)';

    scholarship_type guarda un texto, y un entero aleatorio no tiene sentido en esa columna. Declara la función en USER_FINANCIAL_FEE.

  2. Una columna NOT NULL. La columna staff.password_hash es NOT NULL. Escribe el anonimizador y la sentencia que obtienes para ella.

    Solución del ejercicio 2 
    String statement = PostgresAnonymizer.of(DisclosurePolicy.forLogs())
        .withValue(USER_AUTHORIZATION_PASSWORD, "'*'")
        .label("staff.password_hash", classifier.classify(Staff.class).field("passwordHash").orElseThrow());

    SECURITY LABEL FOR anon ON COLUMN "staff"."password_hash" IS 'MASKED WITH VALUE ''*''';

    El hash es un secreto, así que toda política lo omite; el valor declarado sustituye a NULL. Las comillas simples de '*' se duplican dentro de la etiqueta.

  3. Otra política, otras reglas. Con la política frontDesk del capítulo 7, que enmascara los datos personales de confidencialidad MEDIUM o superior, ¿qué devuelve rule para Student.email y para Student.nationalId?

    Solución del ejercicio 3

    Para email, null: el correo es LOW, la política lo muestra tal cual y no hay regla. Para nationalId, MASKED WITH VALUE NULL: la política lo enmascara y Linneo no conoce una función para user.government_id.national_identification_number.

  4. Una propiedad no personal. ¿Qué miembros tiene la extensión x-linneo de StudentView.page, y cuáles faltan respecto a StudentView.email?

    Solución del ejercicio 4

    {category=system.operations, personal=false, confidentiality=LOW, integrity=LOW, secret=false}. Faltan nature e identifiability, que solo aparecen en datos personales.

  5. Una columna de configuración. MenuGroup guarda id en su columna y el resto de campos en una columna JSON settings. ¿Qué sentencias escribe labels con la política para logs?

    Solución del ejercicio 5 
    SECURITY LABEL FOR anon ON COLUMN "menu_groups"."id" IS NULL;
SECURITY LABEL FOR anon ON COLUMN "menu_groups"."settings" IS NULL;

    Los campos de MenuGroup no son personales y su confidencialidad es LOW, así que todos son CLEAR. Una columna cuyos campos se muestran todos tal cual recibe IS NULL, aunque guarde varios campos.

Autoevaluación

  1. ¿Qué hace PostgresAnonymizer con las sentencias que genera?

    1. Las ejecuta en la base de datos que recibe.
    2. Nada: devuelve el texto y la aplicación lo ejecuta.
    3. Las guarda en un fichero del proyecto.
    Respuesta a la pregunta 1

    La respuesta correcta es la b. Ningún exportador se conecta a nada ni escribe ficheros: devuelven texto, y la aplicación decide dónde y cuándo usarlo.

  2. La política enmascara un campo cuya categoría no tiene función conocida ni declarada. ¿Qué regla recibe?

    1. MASKED WITH FUNCTION anon.dummy_name(), la función más general.
    2. MASKED WITH VALUE NULL, o el valor declarado con withValue.
    3. Ninguna: se muestra tal cual.
    Respuesta a la pregunta 2

    La respuesta correcta es la b. Sin una función, Linneo no conoce el tipo de la columna y aplica la opción más estricta, omitir el valor. Nunca elige una función de otra categoría (a) ni rebaja el tratamiento a mostrar (c).

  3. Tres campos de un compuesto se guardan en una columna JSON. Dos se enmascaran con una función conocida y uno se muestra tal cual. ¿Qué recibe la columna?

    1. La función del primer campo.
    2. IS NULL, porque un campo se muestra tal cual.
    3. MASKED WITH VALUE NULL.
    Respuesta a la pregunta 3

    La respuesta correcta es la c. Una columna compartida solo queda sin regla si todos sus campos son CLEAR; en cualquier otro caso recibe NULL, porque un valor falso del tipo de un campo no sirve para una columna que contiene varios.

  4. ¿Cuándo aparece nature en la extensión x-linneo?

    1. Siempre.
    2. Solo cuando el campo contiene datos personales.
    3. Solo en las categorías especiales.
    Respuesta a la pregunta 4

    La respuesta correcta es la b. nature e identifiability solo aparecen en datos personales, de cualquier naturaleza: ORDINARY, SPECIAL_CATEGORY o CRIMINAL_OFFENCE.

  5. ¿Qué hace OdcsSchema.objectJson con una clave de objeto que el inventario no contiene?

    1. Devuelve un objeto de esquema sin propiedades.
    2. Lanza IllegalArgumentException.
    3. Devuelve null.
    Respuesta a la pregunta 5

    La respuesta correcta es la b. Un objeto vacío (a) o null (c) ocultarían una clave mal escrita, y el contrato publicaría un objeto sin la clasificación de sus propiedades.
